# 0007 — 厚みゼロの cube と、テクスチャ外に出る box UV

対象カバレッジエントリ:

- `minecraft:geometry` の `zero_extent_cube`（**実装済み・実測**）
- `minecraft:geometry` の `box_uv_outside_texture`（**未実装・未測定**）

対応する normative: SC-150 §5.3.1（新規）、§5.3.2（新規）。

## 再現

Blue Archive パック `キヴォトス生徒追加アドオン[B]` のブロック `kivotos:binah_trophy`（ビナーのトロフィー）。
幾何が `models/entity/block/binah_trophy.json`、天板が

```json
{"origin": [-12, 19, -4], "size": [24, 0, 15], "uv": [-15, 11]}
```

**厚みゼロの箱**であり、同じ箱の `uv` 原点が**負**である。この 1 つの cube が 2 つの別々の欠陥を
同時に見せたので、症状を分けて記録する。

| 症状 | 原因 | 状態 |
|---|---|---|
| ハローの**絵が歪む / alpha が効かない** | §5.4 — `render_method` が読まれていない | **未修正**（`0008-render-method`） |
| ハローが**消える** | — | **報告者が撤回した** |

**実害は 1 つ。** 「絵が歪む」だけが実在する症状で、原因は `render_method` を読まないこと（§5.4）
であり、本 feature の整治対象外である。

**「消える」については報告者自身が撤回した。** 当初は「ハローが消える」と報告され、`BlockGeometry`
の厚みゼロ規則がそれを直すとして「1 面を出す」を出荷した。しかしハローは消えていなかった。

## 実測の順序（これが修正より長い）

1. **まず flat-cube を疑った。** 方向は正しかった。
2. **「block path は version-free だから両方の版で出る」と言った。** 我々のコードについては正しい。
   ただし Minecraft のローダまでは version-free ではなく、同じ入力が同じ結果を生むことを前提にして
   いた。
3. **ワールドの有効パック数を原因にした。** 「1.21.11 では 4 パックしか有効化されておらず、モデルに
   到達していなかった」という主張は**ログと矛盾する**。ハローが出ていた 8 月のランは**3 パック**、
   出ていなかった 10 月のランは**6 パック**である。有効化されていないことは原因ではない。
4. **10 月のコンパイル済み class に `BlockGeometry.flatFace(float, float, float)` があった。** 厚み
   ゼロの 2 面の片方を落としている。この時点ではこれが原因の筈だった。
5. **しかし 8 月と 10 月の比較そのものが比較でなかった。** 決定的なのはここである。8 月のインスタンス
   は VulkanMod / EMF / ETF / entityculling / Figura 入りで、リソースパック 2 個も入っていた。
   10 月の dev ランは vanilla + Fabric API のみ。ログからどのモッドが何を変えたかは特定できない。
   **「8 月は正しかった」は我々のコードについての証拠にならない。**

## 実装したもの（**実測ではない**）

`BlockGeometry.element()` は厚みゼロの axis の 2 面を両方そのまま出す。新設計ではない。10 月に
出荷され、その根拠が撤回された「1 面を出す」を戻しただけである。

**Minecraft のブロックモデル baker が退化をどう扱うかは未測定であり、この feature はそれを知って
書いたのではない。** SC-150 §5.3.1 に書いた通り、根拠は不明を明示したうえでの安い選択である。
厚みゼロの axis 1 本について捨てられるのは高々 1 quad で、Path A が受理する 18 モデル全体で
14 本。退化 cube は survey 全体で 420 個あるので、これがコーパスで最も多い形状である。面を 1 つ
捨てることはそれより安くなく、しかも壊れうる版しかない。

検証:

- conformance `block/geometry_flat_cube`（11 assert）。我々が書き出したものの検証であり、
  Minecraft の挙動の検証ではない
- `BlockGeometryTest` の 3 件。実パックの plate を fixture にしてある

**attachable 側だけは「1 面」が正しく、そしてその根拠は我々のコードから直接読める。**
`AttachableRenderTypes.solid()` は `RenderTypes.entityCutoutNoCull` を返すのでカリングがオフであり、
本当に 2 面が深さバッファを争う。どちらかを落とす必要があるので `AttachableGeometry.flatFace` は
残す。同じ commit（`5dfe849`）で書かれた 2 つの半分が逆の答えを要したが、ブロック側にはその
反転の根拠がない。同じ commit だったことは関連性の根拠であって、同一性の根拠ではない。

## 未実装のもの、そしてなぜ

**box UV が 0..16 の外に出る件。** Java は uv を「スプライト全体の 0..16」と読むので、外の値は
スプライト外をサンプリングする。実測 1230 面のうち 25 面が該当（u<0 が 11、u>16 が 10、v>16 が 6）。

**Java 側の挙動は実測済みで確定している。** 1.21.11 の `BlockElementFace.UVs` は 4 つの float を
持つ record で、**検証もクランプも折り返しもしない**。`terrain.fsh` は `Sampler0` をそのまま
サンプルして何も discard しないので、0..1 の外はアトラスの隣接スプライトに着地する。つまり
**欠落ではなく誤った絵**になる。

**トロフィーのハローはこの欠陥の実例ではない。** SC-180 §3.3 の展開はこう置く。

| 面 | テクセル `u` | Java `u` | 面積 |
|---|---|---|---|
| `up` | 0 → 24 | 0 → 6 | 24 × 15（範囲内） |
| `down` | 24 → 48 | 6 → 12 | 24 × 15（範囲内） |
| `north`/`south` | 0 → 24 | 0 → 6 | 高さ 0 |
| `east`/`west` | −15 → 0 | −3.75 → 0 | 高さ 0 |

`u < 0` を持つのは**面積ゼロの 4 面だけ**で、面積ゼロの quad に誤った絵は起きない。ハローが
歪む原因是 §5.4 の `render_method` であって §5.3.2 ではない。この 2 つを取り違えると、UV の算術を
追い続けても出てこない症状を追うことになる。

**なぜまだ直さないか。** Bedrock の「継ぎ目をまたぐ box UV」の解決が未測定だから。候補は 2 つある。

- **折り返す** — テクスチャ幅の整数倍だけずらす。box がテクスチャより狭い間だけ忠実。トロフィーは
  64 に対し 24 幅なので `-15` を `+64` すると 49..73 になり、まだ範囲外。忠実には継ぎ目で分割が
  必要だが、Java の element は 1 面を 2 枚に分割できない
- **拒否する** — `SCE-2031` の §5.2 フォールバック。1 面のためにモデル全体を失い、残り 35 面は正しい

どちらも検証できておらず、答えが異なる。だから field は `missing` のままにして、推測で `partial` を
書かなかった。
