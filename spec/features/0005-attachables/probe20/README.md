# v20 — 骨自身の**宣言回転**が、自身の**アニメ position** を運ぶか（**上下か左右か**だけ）

## 問う文（rig より先に書いた）

> **平たい棒は、立方体の「上」ですか、それとも「横」ですか？**

両者は **24 単位（1.5 ブロック）** 離れている。

| 読み | 棒の位置 | 言っていること |
|---|---|---|
| **上** | `(0, 48, 0)` — 立方体の**真上** | 宣言回転は自身のアニメ position を**運ばない**（移動が最外） |
| **横** | `(±48, 0, 0)` — 立方体の**真横** | 宣言回転は自身のアニメ position を**運ぶ** |

**どちらの読みでも両者は 24 単位離れており、**重ならない**。**
差は**上下か左右かだけ**で、**どの視点・どの距離でも深度の判断が要らない。** v16 の設計。

棒は **16×2×2**（細長い棒）、立方体は **5×5×5**（そのままである）——**大きさが違うので、
「棒」であることが形と大きさの両方で分かる。** 両者とも地上 1.5 ブロック以上の高さにあるので、
**プレイヤーの体の中や足元には入らない。**

棒は `横` のときだけ 90° 立ち上がる。回転ごと骨が消える読みでも `上` と同じ場所に来るので、
**この rig は「運ぶ／運ばない」の 2 つの読みしか区別しない** — そしてそれは充分である。

## rig を 2 度作り直した理由 — **どちらも私が入れた穴**

| | 最初の版 | 穴 | 直し方 |
|---|---|---|---|
| 1 | 基準の立方体が **3×3×3**、model の origin（= プレイヤーの足元）に着地 | **足元に埋めれて見えない。** そして棒と 1 ブロック未満しか離れておらず、視認できない | 立方体を **5×5×5** に拡大し、**地上 1.5 ブロックの上**へ |
| 2 | `loop: "hold_on_last_frame"` ＋ keyframe 無し（length 0） | **未測定の挙動に乗っていた。** 零長さ hold が効くかは §4.1 の `holdsWithoutLength` で、まだ決まっていない。**その問いが実験結果を左右していた** | `animation_length: 5` と `loop: true` を明示。**length 0 の分岐に一切依存しない** |

**どちらの穴も「質問が成立しない」型で、壊れた rig 4 本と同じ形。**
質問の前に設計を検証していなかったのが原因で、**今後は 質問 → 設計の検証 → rig** の順を固定した。

**もう 1 つ、確認して(layout を変えたので): インストール済みの拷贝は repo と
バイト単位で同一だった**（`world_resource_packs/Lepusbind-`、2026-10-04 19:27 展開）。
**つまり「古い版本が入っていた」は原因ではない。** 上の 2 つの穴がそのまま原因だった。

## なぜこの対を選んだか — §4.2.6 が書いている対は答えられない

SC-180 §4.2.6 は次にこう書いている:

> 親が大きなロールに到達し、**そのロールが回す軸に沿った** position を持つ子について ——
> v16 は軸に**直交する**場合を答えた。盾は同じ問いを軸**に沿う**形で出す。

**この対は両読みが一致するので、答えるための質問が成立しない。** 導出できる:

```
親の回転 = Z 軸まわり θ のロール、子のオフセット d = (0, 0, N)   （ロール軸に沿う）
  運ぶ     → R_z(θ)·(0,0,N) = (0, 0, N)     Z 軸まわりの回転は Z を動かさない
  運ばない →                  (0, 0, N)
```

**v16 の `d = (0,24,0)`（軸に直交）は区別できる** — `R_z(θ)·(0,24,0) = (−24 sinθ, 24 cosθ, 0)`
は `θ = 90°` で `(−24, 0, 0)` になり、`d` と直交する。
**軸に沿う場合は `θ` が何であれ区別できない。** ここが §4.2.6 の質問が成立しない理由であり、
このセッションで壊れた rig 4 本（v12 / v14 / v15 / v19）と**まったく同じ形をしている**。
だから §4.2.6 の対は選ばず、HANDOFF の表が残している**未測定の対**を 1 つ選ぶ。
**§4.2.6 の本文は上書きしない**（既に正しい）。

残る未測定の対は 2 つ。**今回は位置の方を 1 つだけ**:


| | 測った | 答え |
|---|---|---|
| 骨自身の**アニメ**回転 → 自身の position | v9/v10 | 運ばない |
| **親の**アニメ回転 → 子の position | v16 | 運ぶ |
| **親の**宣言回転 → 子の position | v14① | 運ぶ |
| **骨自身の宣言回転 → 自身の position** | ← **これ** | **?** ← `bag2` がまさにこれ |

もう 1 つの未測定の対（骨自身の宣言回転 × 自身の**アニメ回転**、順序 `R_bind·R_anim` か逆）は
**触らない。** 理由は 2 つ:

- §4.2.6 の帰属表で、盾の上端を**動かす側の 83 %** は `leftArm2` の**アニメ回転**で、
  盾自身の position は残り 17 %。上の対を測っても帰属の小さい側しか答えが動かない。
- 回転の**合成順序**は v20 の設計（上下か左右か）に収まらない。導出できる — 宣言回転を Z の
  `β`、アニメ回転を Y の `α`、オフセットを真上 `d = (0,24,0)` とすると:

  ```
  R_bind·R_anim → (0, 24 cos α, −24 sin α)      β = 90° のとき
  R_anim·R_bind → (0, 24,        0)
  ```

  **両方とも真上**で、違うのは **Z だけ**。v14 / v15 が三人称カメラで Z を読ませたのと同じ罠で、
  しかも今回は 2 つの候補が**どちらにも上来ない**。触らない。

## 中身（マーカーは 2 つだけ）

```
root  pivot [0,0,0]

m_bind  pivot [0,0,0]  rotation [0,0,90]   ← ジオメトリが宣言した回転（ここに書くのが本題）
        cubes: bar 16x2x2 at origin
        アニメ position [0,48,0]

m_ctrl  pivot [0,0,0]  宣言回転なし          ← 必ず (0,24,0) に着地する基準
        cubes: cube 5x5x5 at origin
        アニメ position [0,24,0]
```

`m_ctrl` は回転する骨を持たないので、どちらの読みでも **(0,24,0)** に着地する。
`m_bind` の棒が**立方体の真上**か**真横**か — それだけを答えます。

**v16 との差は 2 点だけ:** 回転が**親の**骨ではなく**同じ骨**にあり、しかも**アニメ**ではなく
**ジオメトリの宣言**である。位置はどちらもアニメの `position`。
**この 2 点を同時に変えないと v14 の対（親の宣言回転 → 子の position）を再測することになる。**

## 本実装の予測

**「横」**（運ぶ）。`BoneMatrices.local` が
`T(pivot) · R_宣言 · (T_アニメ · R_アニメ · S_アニメ) · T(−pivot)` と合成しているからで、
宣言回転がアニメ position を運ぶ。`:testkit:survey` の実測:

```
lepus:probe20 as geometry.lepus_probe20, third person, main hand, t=0
  plays: [hand always]
  m_bind       x   47.00..  49.00  y   -8.00..   8.00  z   -1.00..   1.00  (1 cubes)
  m_ctrl       x   -2.50..   2.50  y   21.50..  26.50  z   -2.50..   2.50  (1 cubes)
```

`m_ctrl` は `(0, 24, 0)`、`m_bind` は **`x = +48`（横）**。
棒は `x 2 × y 16` に**立っている** = 回転も棒に掛かっている。
一人称でも同じ数字（`compare` で確認済み）。

**これが外れたときは SC-180 §4.1.3 の「移動が最外」を骨宣言回転にも適用することになる。**
その場合、盾の残差の説明が 1 つ増えるのではなく**この 1 つの規則が全 attachable に波及する**ので、
それ以前に出ている数字は全部見直される。bind pose は対称なことが多く、コンパイラも
conformance もこの差を検出しない。
